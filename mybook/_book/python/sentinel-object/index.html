5  감시 객체 패턴 (Sentinel Object Pattern)

전통적인 감시값(Sentinel Value) 패턴의 파이썬 변형

결론

감시 객체 패턴은 표준 라이브러리와 그 너머에서 널리 사용되는 표준 파이썬 접근 방식입니다. 이 패턴은 파이썬의 내장 None 객체를 가장 자주 사용하지만, None 자체가 유효한 값일 수 있는 상황에서는 데이터가 누락되었거나 지정되지 않았음을 나타내기 위해 고유한 object()를 대신 사용할 수 있습니다.

목차:

프로그래밍은 모든 값이 항상 지정되어 있는 도메인에서 가장 쉽습니다. 데이터베이스의 모든 사람이 이름이 있고, 모든 직원의 나이를 알고 있으며, 실험의 매 초마다 데이터가 성공적으로 수집되는 상황 말입니다.

하지만 세상은 그렇게 단순한 경우가 드뭅니다. 따라서 객체의 속성이나 객체 자체가 누락된 경우를 위한 패턴이 필요합니다. 데이터가 부재함을 나타내는 플레이스홀더와 유용한 데이터를 구분하기 위해 어떤 간단한 메커니즘을 사용할 수 있을까요?

5.1 감시값 (Sentinel Value)

전통적인 감시값 패턴은 파이썬 프로그래머들에게 str.find() 메서드를 통해 익숙할 것입니다. 대안인 str.index()는 요청한 부분 문자열을 찾을 수 없을 때 예외를 발생시키는 더 엄격한 방식이지만, find()는 부분 문자열이 없을 때 감시값 -1을 반환함으로써 예외 처리 코드를 작성하는 수고를 덜어줍니다. 이 방식은 종종 코드 한 줄과 약간의 들여쓰기를 줄여줍니다.

try:
    i = a.index(b)
except:
    return

# 반면

i = a.find(b)
if i == -1:
    return

이것이 감시값의 전형적인 예입니다. 값 -1은 함수의 다른 가능한 반환 값들과 마찬가지로 평범한 정수이지만, 미리 약속된 특별한 의미를 갖습니다. 만약 프로그램이 -1을 반환받았는데 이를 확인하는 것을 잊고 문자열의 인덱스로 사용하려고 한다면 큰 문제가 생길 것입니다! 결과는 프로그래머가 의도한 것과 다를 것입니다.

만약 str.find()가 오늘 발명되었다면, 아래에서 설명할 감시 객체 패턴을 사용하여 “찾지 못함”의 의미로 단순히 None을 반환했을 것입니다. 그랬다면 반환 값이 실수로 인덱스로 사용될 가능성이 아예 없었을 것입니다.

감시값은 오늘날 Go 언어에서 특히 흔합니다. Go의 설계는 단순한 참조 대신 항상 문자열 자체를 반환하는 프로그래밍 스타일을 권장하며, 이로 인해 프로그래머는 데이터가 수집되지 않았거나 존재하지 않음을 나타내기 위해 빈 문자열이나 특별한 고유 감시값과 같은 특정 문자열을 선택해야만 합니다.

파이썬에서 Django 프레임워크는 수십 년간의 데이터베이스 관행에 반하여 “문자열 기반 필드에서 null 사용을 피하라”고 권장하는 것으로 유명합니다. 그 결과 Go에서와 마찬가지로 코드가 더 단순해지기도 합니다. None을 확인하는 대신 빈 문자열을 확인하는 코드가 이를 대체하며, 나중에 코드에서 None인 객체에 대해 문자열 메서드를 호출하려다 프로그램이 중단되는 일이 없어집니다.

5.2 널 포인터 패턴 (Null Pointer Pattern)

널 포인터 패턴은 파이썬에서는 불가능하지만, 파이썬과 데이터 모델에 nil이나 NULL 포인터를 도입하여 복잡하게 만드는 언어들 간의 차이점을 설명하기 위해 언급할 가치가 있습니다.

파이썬의 모든 이름은 존재하지 않거나, 존재한다면 반드시 객체를 가리킵니다. del name으로 이름을 제거하거나, 새 객체를 할당할 수 있을 뿐입니다. 파이썬은 다른 대안을 제공하지 않습니다. 이면에서 파이썬의 각 이름은 현재 참조하고 있는 객체의 주소를 저장하는 포인터입니다. 비록 이름이 단순한 None 객체를 가리키고 있더라도, 거기에는 유효한 주소가 들어 있습니다.

이 보장은 파이썬의 기본 C 언어 구현에서 흥미로운 감시 패턴을 지원합니다. C 언어는 이름(C에서는 이를 “포인터”라고 부름)이 항상 유효한 객체의 주소를 가져야 한다는 파이썬의 보장이 없습니다. 이러한 유연성을 활용하여, C 프로그래머들은 주소 0을 “이 포인터는 현재 아무것도 가리키지 않음”이라는 의미로 사용하며, 이 0(또는 많은 C 프로그램에서 정의하는 NULL)이 감시값이 됩니다. 널 포인터일 수 있는 포인터는 사용하기 전에 반드시 확인해야 하며, 그렇지 않으면 프로그램은 segmentation fault와 함께 종료됩니다.

None이나 False조차도 0이 아닌 주소를 가진 실제 객체라는 사실은, C로 구현된 파이썬 함수들이 특별한 의미를 나타내기 위해 NULL 값을 사용할 수 있음을 의미합니다. NULL 포인터는 “이 함수는 작업을 완료하고 값을 반환하지 않았으며, 대신 예외를 발생시켰음”을 의미합니다. 덕분에 파이썬 밑단의 C 코드는 Go 코드에 만연한 “반환 값”과 “에러 여부”를 따로 나타내는 두 개의 값 반환 패턴을 피할 수 있습니다.

# Go는 "반환 값"과 "에러로 종료되었는가"를 
# 별도로 표현해야 합니다.

byte_count, err := fmt.Print("Hello, world!")
if err != nil {
        ...
}

대신, 파이썬을 호출하는 C 언어 루틴은 C 함수가 지원하는 단일 반환 값만 사용하여 정상적인 반환 값과 예외를 구분할 수 있습니다.

# 파이썬 객체에 대한 포인터가 NULL이면 
# "예외가 발생했음"을 의미합니다.

PyObject *my_repr = PyObject_Repr(obj);
if (my_repr == NULL) {
     ...
}

예외 자체는 다른 곳에 저장되며 파이썬 C API를 사용하여 조회할 수 있습니다.

5.3 널 객체 패턴 (Null Object Pattern)

“널 객체”는 비어 있는 값이나 존재하지 않는 항목을 나타내기 위해 사용되는 실제적이고 유효한 객체입니다. 저는 Bobby Woolf의 설명을 인용한 마틴 파울러의 리팩토링이라는 책을 읽으며 이 패턴에 주목하게 되었습니다. 이 패턴은 앞 섹션에서 설명한 “널 포인터”와는 아무런 관련이 없다는 점에 주의하세요! 대신 이는 특별한 종류의 감시 객체를 설명합니다.

보통은 다른 직원을 manager 속성으로 갖지만, 항상 그런 것은 아닌 Employee 객체들의 시퀀스를 상상해 보세요. “관리자 없음”을 나타내는 기본 파이썬 방식은 속성에 None을 할당하는 것입니다.

직원 프로필을 표시하는 루틴은 관리자 객체에 대해 어떤 메서드를 호출하기 전에 감시 객체 None을 확인해야 할 것입니다:

for e in employees:
    if e.manager is None:
        m = '관리자 없음'
    else:
        m = e.manager.display_name()
    print(e.name, '-', m)

그리고 이 패턴은 관리자 속성을 건드리는 모든 곳에서 반복되어야 할 것입니다.

Woolf는 모든 None 관리자 값을 “아무도 없음”이라는 개념을 나타내도록 특별히 설계된 객체로 대체하는 흥미로운 대안을 제시합니다:

NO_MANAGER = Person(name='대행 관리자 없음')

이제 직원 객체들은 None 대신 이 NO_MANAGER 객체를 할당받게 되며, 직원 관리자를 다루는 두 종류의 코드 모두 이득을 봅니다.

  • 단순한 표시나 요약을 생성하는 코드는 NO_MANAGER 관리자 객체를 마치 일반 직원 객체인 것처럼 단순히 출력하거나 집계할 수 있습니다. 널 객체에 대해 코드가 성공적으로 실행될 수 있다면, 특별한 if 문이 필요 없어집니다.
  • 관리자가 없는 직원의 경우를 특별히 처리해야 하는 코드도 이제 조금 더 읽기 쉬워집니다. 일반적인 is None 대신 구체적인 is NO_MANAGER를 사용하여 확인을 수행하므로 가독성이 향상됩니다.

평균이나 다른 통계치를 유효하게 유지하는 널 객체를 설계하는 것이 어려울 수 있는 등 모든 상황에 적합한 것은 아니지만, 널 객체는 파이썬 표준 라이브러리에도 등장합니다. logging 모듈에는 다른 핸들러를 대체할 수 있지만 실제 로깅은 수행하지 않는 NullHandler가 있습니다.

5.4 감시 객체 (Sentinel Objects)

마지막으로 감시 객체 패턴 자체에 대해 알아보겠습니다.

표준 파이썬 감시자는 내장된 None 객체로, 정수, 부동 소수점, 문자열 또는 다른 의미 있는 값에 대한 대안이 필요한 곳 어디에서나 사용됩니다. 대부분의 프로그램에서 이것으로 충분하며, 그 존재 여부는 다음과 같이 확실하게 테스트할 수 있습니다:

if other_object is None:
    ...

하지만 프로그램이 None에 대한 대안을 필요로 하는 두 가지 흥미로운 상황이 있습니다.

첫째, 범용 데이터 저장소는 사용자가 직접 None 객체를 저장하려고 할 수 있기 때문에, 누락된 데이터를 나타내기 위해 None을 사용하는 옵션을 가질 수 없습니다.

예를 들어, 파이썬 표준 라이브러리의 functools.lru_cache()는 내부적으로 감시 객체 패턴을 사용합니다. 클로저 내부에는 캐시 미스(cache miss)를 신호하기 위해 각 캐시 인스턴스마다 별도로 생성되는 완전히 고유한 객체가 숨겨져 있습니다:

sentinel = object()  # 캐시 미스를 알리는 데 사용되는 고유 객체

이 감시 객체를 dict.get()의 두 번째 인자로 제공함으로써 (여기서는 사전 바인딩된 메서드 패턴의 클로저 수준 비공개 예시인 cache_get이라는 이름으로 별칭이 지정됨), 캐시는 결과가 이미 캐시되어 있고 그 값이 마침 None이었던 함수 호출과, 아직 캐시되지 않은 함수 호출을 구분할 수 있습니다:

result = cache_get(key, sentinel)
if result is not sentinel:
    ...

이 패턴은 표준 라이브러리에서 여러 번 나타납니다.

  • 위에서 보았듯이 functools.lru_cache()는 내부적으로 감시 객체를 사용합니다.
  • bz2 모듈은 전역 _sentinel 객체를 가지고 있습니다.
  • configparser 모듈은 모듈 전역 변수로 정의된 _UNSET 감시자를 가지고 있습니다.

감시자가 필요한 두 번째 흥미로운 상황은, 함수나 메서드가 호출자가 선택적 키워드 인자를 제공했는지 여부를 알고 싶을 때입니다. 보통 파이썬 프로그래머들은 그런 인자에 None이라는 기본값을 줍니다. 하지만 당신의 코드가 정말로 그 차이를 알아야 한다면, 감시 객체를 통해 이를 감지할 수 있습니다.

매개변수 기본값에 감시자를 사용하는 것에 대한 초기 설명은 Fredrik Lundh의 “파이썬의 매개변수 기본값”이었으며, 수년에 걸쳐 Ian Bicking의 “마법의 감시자”와 Flavio Curella의 “파이썬의 감시값”가 뒤를 이었습니다. 두 사람 모두 자신의 감시 객체가 읽기 쉬운 repr()을 갖지 못한다는 점을 걱정하며 다양한 해결책을 내놓기도 했습니다.

하지만 응용 분야가 무엇이든, 감시 객체 패턴의 핵심은 주변 코드가 그 의미를 인식하게 해주는 것이 객체의 값이 아니라 정체성(identity)이라는 점입니다. 만약 감시자를 감지하기 위해 동등 연산자(equality operator, ==)를 사용하고 있다면, 당신은 단순히 이 페이지 맨 위에서 설명한 감시값 패턴을 사용하고 있는 것입니다. 감시 객체는 파이썬의 is 연산자를 사용하여 감시자가 존재하는지 감지하는 것으로 정의됩니다.
