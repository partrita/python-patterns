4  사전 바인딩된 메서드 패턴

파이썬 언어 고유의 패턴

결론

공통 객체를 통해 상태를 공유하는 호출 가능 객체들을 모듈의 최상위 수준에서 제공하기 위한 강력한 기법입니다.

파이썬 모듈이 실행 시점에 서로 상태를 공유해야 하는 여러 루틴을 모듈의 전역 네임스페이스에서 제공하고 싶을 때가 있습니다.

가장 유명한 예는 파이썬 표준 라이브러리의 random 모듈일 것입니다. 고급 사용자를 위해 자체 Random 인스턴스를 빌드할 수 있는 옵션을 제공하지만, 대부분의 프로그래머는 모듈의 전역 네임스페이스에서 사용할 수 있는 편리한 루틴들을 선택합니다. 예를 들어 randrange(), randint(), choice() 등이 있으며, 이들은 Random 객체의 메서드들을 그대로 반영합니다.

이러한 최상위 루틴들은 어떻게 상태를 공유할까요?

이면에서 이러한 호출 가능 객체들은 사실 메서드입니다. 모듈 자체가 미리 생성해 놓은 단일 Random 인스턴스에 모두 미리 바인딩(prebound)된 메서드들인 것입니다.

사전 바인딩된 메서드 패턴이 해결하는 문제를 살펴본 후, 파이썬 코드에서 이 패턴이 어떻게 구현되는지 알아보겠습니다.

4.1 대안

한 쌍의 모듈 수준 호출 가능 객체 간에 상태를 공유하는 가장 원시적인 접근 방식은, 모듈의 최상위 수준에 저장된 전역 데이터를 직접 조작하고 수정하는 함수 한 쌍을 작성하는 것입니다.

단순한 난수 생성기를 제공하고 싶다고 가정해 봅시다. 이 생성기는 끝없는 루프를 통해 1부터 255까지의 숫자를 정해진 의사 난수 순서로 반환합니다. 또한 생성기의 상태를 알려진 값으로 재설정하는 간단한 set_seed() 루틴도 제공하고 싶습니다. 이는 난수를 사용하는 테스트나, 재현 가능한 결과를 제공하려는 시뮬레이션에서 중요합니다.

파이썬이 일반 함수만 지원했다면, 공유되는 시드(seed)를 모듈 전역 변수로 저장하고 함수들이 이를 직접 액세스하고 수정하도록 했을 것입니다.

from datetime import datetime

_seed = datetime.now().microsecond % 255 + 1

def set_seed(value):
    global _seed
    _seed = value

def random():
    global _seed
    _seed, carry = divmod(_seed, 2)
    if carry:
        _seed ^= 0xb8
    return _seed

이 방식에는 몇 가지 문제점이 있습니다.

첫째, 이 난수 생성기의 두 번째 복사본을 인스턴스화하는 것이 불가능합니다. 만약 두 개의 스레드가 각각 잠금(lock)으로 보호할 필요가 없는 자신만의 생성기를 원한다면, 방법이 없습니다.

(사실, 파이썬에서는 가능합니다. 가능성을 생각해 보세요! 모듈을 임포트하고, 참조를 저장하고, sys.modules 딕셔너리에서 제거한 다음, 다시 임포트하여 두 번째 복사본을 얻을 수 있습니다. 또는 수동으로 두 번째 모듈 객체를 인스턴스화하고 세 개의 이름을 모두 복사할 수도 있습니다. 여기서 “방법이 없다”는 것은 제정신인 파이썬스러운 접근 방식을 의미합니다.)

둘째, 생성기의 상태가 전역적이면 난수 생성기 테스트들을 서로 분리하기가 더 어렵습니다. 각 테스트가 별도의 격리된 인스턴스를 생성하고 실행하는 대신, 모든 테스트가 단일 생성기를 공유해야 하며 다음 테스트가 실행되기 전에 상태를 정확하게 재설정해야 합니다.

셋째, 이 접근 방식은 캡슐화를 포기합니다. 이는 이전 두 가지 불만보다 모호하게 들릴 수 있지만, 수십 개의 다른 객체가 포함될 수 있는 모듈에서 두 개의 함수와 한 개의 seed로 구성된 작고 긴밀한 시스템이 서로 관련이 없어 보이는 세 개의 이름으로 흩어져 있는 것은 가독성(“가독성이 중요하다”)을 해칠 수 있습니다.

위의 문제들을 해결하기 위해, 두 함수를 들여쓰고 새로운 파이썬 클래스의 메서드로 래핑합니다. 그러면 두 메서드와 그 상태를 행복하게 하나로 묶을 수 있습니다.

from datetime import datetime

class Random8(object):
    def __init__(self):
        self.set_seed(datetime.now().microsecond % 255 + 1)

    def set_seed(self, value):
        self.seed = value

    def random(self):
        self.seed, carry = divmod(self.seed, 2)
        if carry:
            self.seed ^= 0xb8
        return self.seed

이 방식은 호출자에게 추가 단계를 요구합니다. 두 메서드를 호출하기 전에 객체를 인스턴스화해야 합니다. 호출자가 그 단계를 건너뛰게 할 수 있는 방법이 있을까요?

소프트웨어 엔지니어라면 대다수의 경우 이와 같이 클래스를 정의하는 것만으로 충분하다는 사실을 잠시 멈추고 진지하게 생각해 볼 필요가 있습니다. 사용자가 클래스의 인스턴스를 만드는 데는 단 한 줄의 문장만 필요합니다. 만약 그들의 애플리케이션 아키텍처가 너무 엉망이라 필요한 곳마다 인스턴스 쉽게 전달할 수 없다면, 그들은 언제든지 자신의 모듈 중 하나에 인스턴스를 모듈 전역 변수로 저장하여 나머지 코드에서 사용할 수 있습니다.

난수 생성기에 사전 바인딩된 메서드 패턴이 특히 잘 어울리는 몇 가지 이유가 있습니다.

  1. 난수 생성기를 인스턴스화하려면 시스템 호출이 필요합니다. 우리의 경우 날짜를 묻는 것이고, 파이썬 random 모듈의 경우 시스템 엔트로피 풀에서 바이트를 가져오는 것입니다. 난수가 필요한 모든 모듈이 자체 Random 객체를 인스턴스화해야 한다면, 이 비용이 반복적으로 발생할 것입니다.
  2. 의사 난수 생성기는 공유될 때 그 동작이 더 바람직할 수 있는 흥미로운 리소스의 사례입니다. 당신이 인스턴스의 유일한 호출자라면, 완전히 예측 가능한 반복되는 값의 시퀀스를 보게 됩니다. 대신 그 인스턴스를 다른 코드와 공유하고 있다면, 다른 호출자들이 생성기를 호출할 때마다 생성기가 시퀀스에서 예측할 수 없게 앞질러 가는 것처럼 보일 것입니다.
  3. random의 대부분의 사용자(표준 라이브러리 내의 여러 모듈 포함)는 모듈 수준의 호출을 사용하기 위해 임포트하므로, 그것들을 구동하는 미리 빌드된 Random 인스턴스가 사용되지 않은 채 방치되는 경우는 드뭅니다.

만약 당신이 설계 중인 모듈에서도 비용과 이점의 균형이 이와 비슷하다면, 사전 바인딩된 메서드 패턴을 통해 놀라운 편리함을 제공할 수 있습니다.

4.2 패턴

사용자에게 사전 바인딩된 메서드 세트를 제공하려면 다음을 수행하십시오.

  • 모듈의 최상위 수준에서 클래스를 인스턴스화합니다.
  • 사용자가 객체에 직접 간섭하지 않도록 밑줄(_)로 시작하는 비공개 이름을 할당하는 것을 고려하십시오.
  • 마지막으로, 객체 메서드의 바인딩된 복사본을 모듈의 전역 네임스페이스에 할당합니다.

위에서 예로 든 난수 생성기의 경우, 전체 모듈은 다음과 같을 것입니다.

_instance = Random8()

random = _instance.random
set_seed = _instance.set_seed

이제 사용자들은 각 메서드를 독립 실행형 함수처럼 호출할 수 있습니다. 하지만 메서드들은 바인딩된 공통 인스턴스 덕분에 사용자가 상태를 명시적으로 관리하거나 전달할 필요 없이 비밀리에 상태를 공유할 것입니다.

이 패턴을 연습할 때, 임포트 시점에 객체를 인스턴스화하는 위험에 대해 책임을 져야 합니다. 생성자가 파일을 생성하거나, 데이터베이스 구성을 읽거나, 소켓을 열거나, 일반적으로 임포트하는 프로그램에 부작용을 일으키는 클래스에는 이 패턴이 적합하지 않습니다. 그런 경우에는 사전 바인딩된 메서드 패턴을 아예 피하거나, 메서드 중 하나가 호출될 때까지 실제 부작용을 지연시키는 것이 좋습니다. 애플리케이션 프로그래머에게 다른 루틴이 작동하기 전에 setup() 메서드를 호출하도록 요구하는 중간적인 방법을 선택할 수도 있습니다.

하지만 상당한 지연이나 복잡성 없이 인스턴스화할 수 있는 경량 객체의 경우, 사전 바인딩된 메서드 패턴은 클래스 인스턴스의 상태 기반 동작을 모듈의 전역 수준에서 사용할 수 있게 만드는 우아한 방법입니다.

이 패턴의 예는 우리가 예로 든 random 모듈 외에도 표준 라이브러리 곳곳에 즐겁게 흩어져 있습니다. calendar.py 모듈이 이를 사용합니다:

c = TextCalendar()

...

monthcalendar = c.monthdayscalendar
prweek = c.prweek
week = c.formatweek
weekheader = c.formatweekheader
prmonth = c.prmonth
month = c.formatmonth
calendar = c.formatyear
prcal = c.pryear

오래된 reprlib.py도 단일 repr() 루틴을 제공하기 위해 사용합니다:

aRepr = Repr()
repr = aRepr.repr

다른 여러 모듈에서도 볼 수 있습니다. 표준 라이브러리의 다음 객체들에서 사전 바인딩된 메서드 패턴이 사용되는 것을 찾을 수 있습니다.

  • distutils.log._global_log
  • multiprocessing.forkserver._forkserver
  • multiprocessing.semaphore_tracker._semaphore_tracker
  • secrets._sysrand

마지막 힌트: 메서드를 전역 이름에 명시적으로 할당하는 것이 거의 항상 더 좋습니다. 메서드가 12개나 되더라도, 모듈의 왼쪽 열에 맞춰 당신이 정의하는 전역 이름의 전체 목록을 가시적으로 보여주는 12개의 할당문을 빠르게 작성하는 것을 권장합니다. 파이썬이 동적 언어라는 사실 때문에 속성 성찰(introspection)과 for 루프를 사용하여 일련의 할당을 자동화하고 싶은 유혹이 생길 수 있습니다. 저는 이를 반대합니다. 파이썬 프로그래머는 “명시적인 것이 암시적인 것보다 낫다”고 믿습니다. 이름 더미를 실제 코드로 구체화하는 것이 인간 독자, 언어 서버, 그리고 오래된 grep에게도 더 도움이 될 것입니다.
